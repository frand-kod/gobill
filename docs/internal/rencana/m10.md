# Rencana M10: API penuh, pemisahan proses, dan frontend

- **Status:** Draf, menunggu keputusan
- **Tanggal:** 2026-11-13

Lanjutan dari [modularisasi.md](modularisasi.md). M0 sampai M9 sudah selesai.

## Masalah

Target M10 adalah server API terpisah dan frontend terpisah. Tapi ada batasan nyata:

- Target utama adalah STB dengan RAM 1–2 GB. Satu binary dan satu proses adalah alasan utama memilih Go. Lihat [keputusan-stack.md](keputusan-stack.md).
- SQLite hanya aman ditulis oleh satu proses. Dua proses yang menulis file DB yang sama akan saling menunggu lock.
- Ada state di memori: `notify.chans`, `job.states`, limiter login, `formTokens`, dan metrics. State ini hilang atau terbelah kalau proses dipecah.
- API v1 sekarang hanya baca. Belum ada endpoint tulis.

Jadi "memecah proses" bukan langkah pertama. Langkah pertama adalah membuat API cukup lengkap. Setelah itu frontend bisa dipisah tanpa memecah proses.

## Prinsip

- Tetap satu binary. Pemisahan dilakukan lewat batas kode, bukan lewat proses.
- Satu proses menulis ke DB. Proses lain, kalau ada, bicara lewat HTTP ke proses itu.
- API memakai `service` yang sama dengan handler HTML. Tidak ada logika bisnis di handler API.
- HTML server-side tetap jalan selama frontend baru belum menggantikannya. Tidak ada big bang.
- Setiap langkah bisa di-merge dan di-rilis sendiri.

## Opsi arsitektur

### A. Satu proses, frontend memakai API (DIREKOMENDASIKAN)

Binary tetap satu. `/api/v1` dilengkapi sampai bisa dipakai frontend apa pun. Frontend baru, misalnya aplikasi mobile atau SPA, cukup memanggil API. Halaman HTML lama tetap ada.

- Kelebihan: tidak ada masalah SQLite dan state memori. Cocok untuk STB.
- Kekurangan: API dan RADIUS tetap berbagi proses dan CPU.

### B. Satu binary, beberapa peran

Binary yang sama bisa dijalankan dengan peran: `gobill serve --role=all|core|edge`.
- `core` memegang DB, RADIUS, job, dan API internal.
- `edge` hanya melayani HTTP publik atau portal, lalu meneruskan ke `core`.

- Kelebihan: portal bisa diskalakan atau dipisah dari RADIUS.
- Kekurangan: butuh API internal dan auth antar proses. Ini hanya berguna untuk VPS besar, bukan STB.

### C. Proses terpisah dengan DB server

API dan RADIUS jadi proses terpisah, dan SQLite diganti PostgreSQL.

- Kekurangan: melanggar target STB, dan semua query sqlc harus ditulis ulang. Tidak direkomendasikan.

Rekomendasi: kerjakan A sekarang. B hanya kalau nanti ada kebutuhan nyata. Desain A tidak menutup jalan ke B.

## Klien pertama: chat WhatsApp

Untuk ISP kecil, alat paling berguna adalah chat WhatsApp. Admin dan pelanggan sudah memakainya setiap hari, jadi tidak perlu aplikasi baru. gobill sudah bisa mengirim WA lewat `alt_wga_server_url` atau `wa_url`. Yang belum ada adalah menerima pesan.

Alurnya:

```
WA gateway ─► POST /wa/inbound (webhook, ber-secret)
               │
               ├─ nomor dikenali sebagai admin   ─► tool admin (scope dari role)
               ├─ nomor dikenali sebagai pelanggan ─► tool pelanggan (hanya datanya sendiri)
               └─ tidak dikenal ─► balasan umum, tanpa data
               │
               ▼
       daftar tool bersama ─► service/*  ─► balasan lewat notify.WhatsApp
```

Gateway: GOWA ([go-whatsapp-web-multidevice](https://github.com/aldinokemal/go-whatsapp-web-multidevice)), yang sudah dipakai untuk kirim. GOWA ditulis dalam Go dan berlisensi MIT.
- Webhook masuk diatur dengan `WHATSAPP_WEBHOOK`. Event dibatasi dengan `WHATSAPP_WEBHOOK_EVENTS=message`.
- Request ditandatangani HMAC-SHA256 di header `X-Hub-Signature-256`, dengan kunci `WHATSAPP_WEBHOOK_SECRET`. gobill wajib memverifikasinya. Kunci ini wajib diisi, karena tanpa itu GOWA membuat kunci acak setiap start.
- Format payload pesan teks ada di `docs/webhook-payload.md` milik GOWA. Baca dokumen itu, dan pakai versi GOWA yang terkunci, sebelum menulis parser.

Alternatif yang ditimbang:
- Gateway berbasis Rust: tidak ada yang matang, dan GOWA sudah ringan. Beban kerjanya kecil, jadi bahasa tidak berpengaruh.
- whatsmeow di dalam binary gobill: tanpa proses tambahan. Tapi protokol WA tidak resmi berubah sering, risiko blokir nomor pindah ke gobill, dan gobill harus punya halaman login QR. Pertimbangkan hanya kalau banyak pengguna minta.
- WhatsApp Cloud API resmi: butuh verifikasi bisnis Meta, berbayar per percakapan, dan webhook HTTPS publik. Sulit untuk STB di balik NAT.

Daftar tool ditulis sekali dan dipakai oleh tiga jalur: perintah WA, MCP, dan API. Contoh tool:
- Pelanggan: `cek` (status dan sisa masa aktif), `tagihan`, `kuota`, `bayar` (kirim link atau QRIS), `paket`.
- Admin: `cari <nama>`, `isolir hari ini`, `perpanjang <id> <paket>`, `buka isolir <id>`, `ringkasan`.

Dua mode, dipilih di setting:
1. **Perintah**: kata kunci tetap, misalnya `cek` atau `tagihan`. Tanpa AI, tanpa biaya, jalan di STB. Ini dikerjakan lebih dulu.
2. **AI**: pesan bebas diteruskan ke LLM yang memakai daftar tool yang sama. Opsional, butuh API key, dan hanya untuk tool yang diizinkan.

Keamanan:
- Webhook wajib punya secret. Request tanpa secret yang benar ditolak.
- Nomor pengirim dari gateway tidak bisa dibuktikan sepenuhnya. Aksi admin yang mengubah data atau uang butuh konfirmasi. Contoh: balasan "ketik 4821 untuk konfirmasi", kode sekali pakai yang kedaluwarsa dalam 5 menit.
- Pelanggan hanya bisa melihat dan membayar datanya sendiri.
- Rate limit per nomor memakai limiter reserve.
- Setiap aksi dicatat di log admin dengan sumber `wa`.
- Pada mode AI, isi pesan dan data pelanggan adalah data, bukan perintah. Tool tulis tetap butuh konfirmasi kode.

## Tahap

### M10.1 API tulis untuk admin

- Tambah endpoint tulis di `/api/v1` yang memanggil `service/*`: customer, plan, subscription (recharge, perpanjang, isolir), voucher, dan pembayaran manual.
- Izin memakai permission role API yang sudah ada di `/admin/api`. Tiap endpoint tulis butuh scope tulis sendiri, misalnya `customers:write`.
- Error dikembalikan sebagai JSON dengan kode yang tetap, misalnya `{"error":"plan_not_found"}`. Pesan i18n tidak dipakai di API.
- Setiap aksi tulis lewat API dicatat di log admin, sama seperti aksi dari HTML.
- Idempotency key untuk aksi uang, yaitu recharge dan pembayaran. Retry dari klien tidak boleh menagih dua kali.

### M10.2 API portal pelanggan

- Auth pelanggan untuk API: token sesi pendek yang terpisah dari token admin `gbt_`.
- Endpoint: profil, langganan, pemakaian, riwayat transaksi, beli paket, dan status pembayaran.
- Rate limit memakai limiter reserve yang sudah ada.

### M10.3 Kontrak API

- Spesifikasi OpenAPI ditulis tangan di `docs/api/openapi.yaml`. Tidak ada code generation.
- Test kontrak: setiap route di `web/api` harus ada di spesifikasi, dan sebaliknya.
- Versi: perubahan yang merusak klien hanya boleh di `/api/v2`.

### M10.4 State memori yang aman untuk banyak klien

Ini syarat sebelum opsi B. Kerjakan hanya kalau B jadi dipilih.

- Limiter login dan `formTokens` disimpan di DB, atau tetap per proses dengan batas yang jelas.
- `job.states` dan `notify.chans` hanya hidup di proses `core`.
- Metrics per proses, dengan label peran.

### M10.5 Deps per paket

- `web/core` dan `adminx` dipecah menjadi struct `Deps` kecil per paket handler.
- Tujuannya agar jelas domain apa saja yang dipakai `web/api` dan portal.
- Aturan baru: `web/api` tidak boleh meng-import `radius`, `device`, atau `wg` secara langsung. Semua lewat `service`.

### M10.6 Frontend baru (opsional)

Hanya kalau ada kebutuhan nyata, misalnya aplikasi mobile pelanggan.

- Aplikasi mobile atau SPA memakai `/api/v1` saja.
- HTML lama tetap jadi frontend default di STB, karena tanpa build step JS.
- Halaman HTML yang sudah memakai `fetch` boleh dipindah ke API lebih dulu: search, sessions, usage, maps.

### M10.7 MCP server (opsional)

MCP membuat asisten AI bisa memakai gobill, misalnya "cek pelanggan yang isolir hari ini" atau "perpanjang paket budi". MCP hanyalah klien lain di atas API. Tidak ada logika baru.

- Endpoint `/mcp` di binary yang sama, memakai transport HTTP streamable.
- Setiap tool MCP memanggil `service` yang sama dengan endpoint `/api/v1`. Daftar tool diambil dari kontrak M10.3.
- Auth memakai token API `gbt_` dan scope yang sama. Token MCP dibuat di `/admin/api` seperti token lain.
- Mulai dari tool baca saja. Tool tulis menyusul, dan aksi uang wajib memakai idempotency key.
- Data pelanggan, misalnya nama atau catatan, bisa berisi teks yang mencoba memerintah AI. Hasil tool dikirim sebagai data, dan tool tulis butuh scope tulis yang terpisah.
- Library MCP untuk Go dipilih saat tahap ini mulai, setelah membaca dokumentasi resminya.

Syarat: M10.1 dan M10.3 selesai. Kalau API dan kontraknya rapi, MCP hanya lapisan tipis.

## Urutan

```
M10.1 ─► M10.2 ─► M10.3
   └────► M10.5
M10.4 hanya jika opsi B dipilih
M10.6 hanya jika ada klien nyata
M10.3 ─► M10.7 (MCP)
```

M10.1 dan M10.3 paling bernilai. Integrasi pihak ketiga, misalnya bot WhatsApp atau sistem akuntansi, sudah bisa memakai API setelah dua tahap ini.

## Keamanan

- Endpoint tulis butuh scope tulis. Token baca saja tidak boleh menulis.
- Token admin dan token pelanggan tidak boleh tertukar. Test harus memastikan token pelanggan ditolak di endpoint admin.
- DTO tetap tanpa field rahasia. Test refleksi DTO yang sudah ada tetap berlaku untuk DTO input.
- Aksi uang memakai idempotency key dan transaksi `_txlock=immediate`.
- CORS mati secara default. Origin hanya diizinkan lewat setting.

## Urutan yang disarankan

1. Daftar tool bersama di atas `service/*`, dengan tool baca untuk pelanggan dan admin.
2. Webhook `/wa/inbound` dengan mode perintah.
3. Tool tulis admin dengan konfirmasi kode.
4. M10.1 dan M10.3: tool yang sama dibuka di `/api/v1`.
5. M10.7 MCP dan mode AI di WA, memakai tool yang sama.
